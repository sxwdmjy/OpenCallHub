# openCallHub 重构人员主责与总体排期

日期：2026-06-05

## 1. 文档目的

本文档用于沉淀 openCallHub 重构期间的人员配置、员工负责范围、总体排期、阶段负责人和协作规则，方便后续参与人员快速接手。

本文档是协作入口文档，不替代详细阶段计划。具体实现任务仍以 `docs/superpowers/plans/2026-05-19-opencallhub-phase-*.md` 为准；本文档负责说明“谁负责什么、什么时候做、按什么原则做”。

## 2. 使用说明

1. 新成员加入项目时，先阅读本文档，确认自己所属人员或角色的负责范围。
2. 再阅读系统设计文档：`docs/superpowers/specs/2026-05-19-opencallhub-refactor-design.md`。
3. 最后阅读当前阶段对应的详细计划，例如 Phase 1 阅读 `docs/superpowers/plans/2026-05-19-opencallhub-phase-1-foundation.md`。
4. 如果真实团队成员发生变化，只替换本文档中的员工姓名，不改变职责边界。
5. 如果模块边界、阶段验收标准或总排期变化，需要同步更新本文档和主实施计划。

## 3. 重构总原则

1. 代码必须美观、合理、简洁，优先解决真实复杂度，不为了“看起来高级”而引入多余抽象。
2. 代码风格参考旧代码，保留当前项目中已有的 `Controller / Service / Mapper / Entity / Query / Vo` 分层和命名习惯。
3. 中文注释使用 UTF-8 编码，重点解释业务规则、状态流转、边界约束、并发控制、幂等条件和不容易一眼看懂的设计意图。
4. 普通 getter/setter、简单 CRUD、变量含义清晰的方法不写重复注释，避免注释噪音。
5. Controller 只负责参数接收、权限入口、响应封装，不直接编排复杂业务流程。
6. 复杂流程下沉到应用服务、领域服务、策略组件、状态机或事件处理器。
7. 合理使用 23 种设计模式中的适用模式，不为了覆盖全部设计模式而强行引入复杂度。
8. 每个阶段必须有可运行、可验证、可演示的验收结果，不能只完成代码堆叠。
9. 涉及号码、客户、录音、AI 文本、导出文件、密钥配置的代码必须优先考虑权限、脱敏和审计。
10. 通信链路必须贯穿 `traceId`、`callId`、`uuid`、`legId`、`agentId`、`taskId` 等关键标识。

## 5. 员工负责范围明细

### 5.1 周工：架构与重构总负责人

周工负责整体重构方向，所有涉及模块边界、状态机、事件一致性、跨模块调用、设计模式引入的任务都必须经过周工确认。周工不负责堆业务代码，而负责保证每个阶段的代码结构清晰、复杂度可控、未来可拆分。

周工需要重点把控以下事项：

- `och-esl` 只处理 FreeSWITCH ESL 通信和事件归一化，不承载外呼、IVR、ACD 业务策略。
- `och-call` 负责通话会话、通话腿、通话事件、通话状态机和电话控制应用边界。
- `och-ivr` 负责流程版本、节点、边、变量、执行轨迹和 IVR 运行时。
- `och-acd` 负责技能组、队列、坐席状态、分配策略、溢出和 SLA。
- `och-call-task` 负责外呼任务、任务状态、名单、过滤、调度和进度。
- `och-ai` 负责 AI 插件、机器人会话、AI 调用日志、摘要、标签和成本。
- 设计模式必须服务业务变化点，禁止为了形式强行套模式。

### 5.2 王工：基础工程与公共能力

王工负责所有阶段复用的基础能力。后续业务模块不得重复实现统一响应、traceId、Redis、RabbitMQ、文件存储、异常处理等公共能力。

王工负责范围包括：

- Maven 父工程和多模块依赖治理。
- `ResResult`、`BaseController`、统一异常、统一响应包装。
- `TraceInterceptor`、traceId 生成、传递、响应头写入和日志关联。
- Redis 操作封装、RabbitMQ 事件发布抽象、outbox 扩展点。
- Flyway 数据库迁移机制和基础表迁移验证。
- 本地启动配置、OpenAPI 暴露和后端启动稳定性。

### 5.3 李工：系统权限与资源管理

李工负责系统管理和资源管理，是所有业务模块访问控制的基础。任何新增菜单、按钮、数据范围、资源删除校验、敏感配置展示都需要李工参与。

李工负责范围包括：

- 用户、角色、部门、菜单、按钮权限、角色菜单绑定。
- 数据范围过滤，包括部门、技能组、客户池、外呼任务、报表范围。
- 操作审计、登录日志、资源审计。
- SIP 账号、分机、号码、号码池、中继网关、FreeSWITCH 节点、Kamailio 节点。
- 音频素材、存储配置、AI 插件资源配置。
- 资源依赖检查，防止号码、线路、分机、音频、AI 插件被业务引用时误删。

### 5.4 陈工：通信链路与 ESL 边界

陈工负责通信层正确性和稳定性。通信层代码必须保留 FreeSWITCH 原始事件，同时提供业务模块可理解的归一化事件。

陈工负责范围包括：

- FreeSWITCH ESL 连接、断线恢复和事件监听。
- CHANNEL_CREATE、CHANNEL_ANSWER、CHANNEL_HANGUP、DTMF、RECORD 等事件归一化。
- originate、answer、hangup、hold、unhold、mute、unmute、bridge、transfer 等命令封装。
- 呼叫 uuid、legId、callId 的映射和追踪。
- 通信事件重复、乱序、丢失的处理建议。
- 录音失败、桥接失败、DTMF 失败等异常链路的恢复策略。

### 5.5 赵工：呼入、IVR 与 ACD

赵工负责呼入业务主链路，从号码进入系统到 IVR、ACD、坐席接入前的完整闭环。

赵工负责范围包括：

- 通话状态机和呼入会话创建。
- IVR 流程、流程版本、节点、边、变量、执行轨迹。
- IVR 菜单节点、播放节点、收号节点、条件节点、日程节点、转人工节点、转技能组节点、语音信箱节点、挂机节点。
- ACD 技能组、队列、坐席可用状态、分配策略、溢出规则、SLA 规则。
- 队列实时监控和 `/ws/monitor` 推送。
- 呼入链路 E2E 验收：呼入 → IVR → ACD → 坐席可接入。

### 5.6 孙工：外呼、报表与批处理

孙工负责外呼中心和异步任务类能力。外呼必须优先保证不重复拨打、不过量拨打、不越权拨打。

孙工负责范围包括：

- 外呼任务模型、任务状态机、任务明细、拨打记录。
- 客户名单导入、导入错误明细、导入进度。
- DNC、黑名单、时间窗、重复号码、数据范围过滤。
- 预览外呼领取、拨打、结果回写。
- 预测外呼并发租约、调速算法、放弃率保护。
- 机器人外呼调度和 AI 会话交接边界。
- `/ws/task` 任务进度推送、外呼统计聚合。
- 报表聚合和批处理任务进度、失败重试。

### 5.7 刘工：AI 联络中心

刘工负责 AI 能力抽象和机器人会话闭环。AI 代码必须隔离供应商差异，不能让业务流程直接依赖某一个具体厂商 SDK。

刘工负责范围包括：

- ASR、TTS、LLM、Workflow 插件抽象。
- Dify、RAGFlow、LangFlow 适配器。
- 机器人会话、轮次、上下文、变量、意图、标签、摘要。
- AI 插件调用日志、延迟、失败原因、供应商响应摘要。
- 静音、无响应、打断、转人工条件。
- AI 质检、AI 成本统计、AI 内容审计。
- AI 密钥加密存储和脱敏展示必须与郑工、李工协作完成。

### 5.8 张工：前端控制台与工作台

张工负责前端整体体验和页面交付。前端需要同时满足管理控制台和坐席沉浸式工作台两类入口。

张工负责范围包括：

- Vue 3 工程结构、路由、Pinia 状态、Axios 请求封装、WebSocket 封装。
- 登录页、首页、布局、菜单、权限路由。
- 系统权限中心、资源管理中心。
- IVR 流程设计器、节点配置抽屉、测试运行、轨迹回放。
- ACD 配置和队列监控页面。
- 坐席工作台、电话条、弹屏、客户卡片、转接面板、后处理面板。
- 外呼任务向导、预览外呼页、预测外呼监控、机器人会话列表。
- AI 会话轨迹、客户、工单、知识库、质检、报表、合规页面。

### 5.9 郑工：部署、运维、安全与合规

郑工负责私有化部署质量和安全底线。所有涉及密钥、录音、导出、客户敏感字段、AI 文本的功能，都必须经过郑工安全确认。

郑工负责范围包括：

- Docker Compose、Nginx、前端静态部署、后端环境变量。
- MySQL、Redis、RabbitMQ、FreeSWITCH、Kamailio、MinIO 的部署和健康检查。
- Prometheus、Grafana、日志采集、告警规则。
- 数据库备份、录音备份、恢复演练、回滚方案。
- HTTPS、密钥管理、AI Token 加密、日志脱敏。
- 手机号、客户姓名、身份证、邮箱、录音、导出文件的权限和审计。
- 性能压测、安全测试和生产验收清单。

### 5.10 吴工：质量保障与验收

吴工负责把每个阶段的验收标准转成可执行测试和验收证据。没有测试和验收证据的阶段不能进入下一阶段。

吴工负责范围包括：

- 后端单元测试、集成测试、API 契约测试。
- MockMvc、Spring Boot Test、关键领域服务测试。
- 前端 Vitest、Playwright E2E。
- 呼入、IVR、ACD、坐席工作台、外呼三模式、AI 插件、权限越权、导出合规等核心回归。
- ESL 断连、事件重复/乱序、录音失败、插件超时等故障演练。
- 阶段验收报告和缺陷闭环。

## 8. 设计模式使用边界

| 设计模式 | 适用业务点 | 负责员工 | 使用原则 |
|---|---|---|---|
| 策略模式 | ACD 分配策略、外呼过滤、AI 插件选择、文件上传类型 | 赵工、孙工、刘工、王工 | 同一业务动作存在多种可替换算法时使用 |
| 模板方法 | 文件上传/TTS、导入导出批处理、质检评分流程 | 王工、孙工、刘工 | 流程骨架固定、局部步骤变化时使用 |
| 工厂模式 | IVR 节点处理器、AI 插件适配器、外呼任务处理器 | 赵工、刘工、孙工 | 创建逻辑复杂或需要按类型选择实现时使用 |
| 适配器模式 | Dify/RAGFlow/LangFlow、ASR/TTS 厂商、FreeSWITCH ESL 事件 | 刘工、陈工 | 隔离外部系统差异，保护内部接口稳定 |
| 状态模式 | 通话状态、坐席状态、IVR 执行状态、外呼任务状态 | 周工、赵工、孙工 | 状态转换复杂且有明确规则时使用 |
| 命令模式 | 电话条控制命令、ESL 控制命令 | 陈工、赵工 | 控制动作需要排队、记录、重试或审计时使用 |
| 观察者 / 发布订阅 | RabbitMQ 事件、WebSocket 推送、任务进度通知 | 王工、孙工、张工 | 业务事件需要异步扩展时使用 |
| 责任链模式 | 外呼过滤、权限校验、导出合规检查 | 孙工、李工、郑工 | 多个校验步骤可组合、可短路时使用 |
| 门面模式 | Controller 面向应用服务的聚合入口 | 周工、王工、各模块负责人 | 隐藏跨模块编排，避免 Controller 变厚 |

不建议为了凑齐 23 种设计模式而强行引入复杂度。单例、原型、访问者、解释器等模式只有在出现明确业务需要时再引入。

## 9. 后续人员参与流程

1. 确认自己对应员工或角色，阅读第 4 节和第 5 节负责范围。
2. 阅读第 6 节总体排期，确认当前项目处于哪个阶段。
3. 阅读当前阶段对应的详细计划文件。
4. 开发前先读旧代码风格，不要直接按个人习惯重写。
5. 开发时优先小步提交，避免跨阶段、跨模块混改。
6. 涉及公共能力、通信链路、权限安全、AI 插件、导入导出、录音、客户敏感数据时，必须找对应负责人评审。
7. 每个阶段完成后，由吴工组织测试和验收证据，由周工确认是否进入下一阶段。

## 10. 文档维护规则

1. 员工变更时，只更新员工姓名和必要的联系方式，不随意改变职责边界。
2. 阶段排期变化时，更新第 6 节和第 7 节，并同步检查主实施计划。
3. 第 6-9 阶段独立计划补齐后，需要把对应文档路径补入本文档。
4. 阶段完成后，只记录阶段状态和关键结论，不把详细实现复制到本文档。
5. 如果实际代码与本文档职责边界冲突，以周工评审后的最新结论为准，并及时更新本文档。
